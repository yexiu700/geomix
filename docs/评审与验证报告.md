> 评审依据：`site/site-map.md`（188 行）、`site/00~27*.png`（28 张截图，已逐张打开核对）、`docs/01~05`（5 份飞书文档原文），以及用户给调研员的原始需求（`agy/brief2.md` 第 15 行：“计费前期可不实收，但点数扣减逻辑要设计好、可开关”；一期底座包含“多标签页导航”）。
> 评审期间未访问原站，没有消耗任何点数。

## 1. 评审方法

### 1.1 取证规则
- **实测事实**只认截图和 site-map。截图与 site-map 不一致时，以截图为准（例如 site-map 第 127 行写「开始写作（10点/篇）」，截图 `17-ai-writing-task-add.png` 实际是「开始写作（10点数/篇）」）。
- **业务规则**以 docs 原文为准，引用时写到文件名和行号。报告引错文件或行号的，记为「出处错误」。
- 调研员自己的设计（推测）本身不算错，但如果写成“原站如此”又拿不出依据，记为「过度推测」。
- 报告内部前后说法冲突、或者引用了不存在的章节/文件，记为「自相矛盾」。

### 1.2 六个评审维度（每项 1–10 分）

| 维度 | 含义 | 主要检查点 |
|---|---|---|
| D1 准确性 / 与实测一致 | 字段、默认值、文案、路由、价格、配额是否与截图一致 | 逐字段对照 28 张截图；site-map 行号 |
| D2 完整性 | 一期四模块、底座、计费、实测计划、待确认问题是否都覆盖 | 工具栏按钮、列表列、表单字段、二级页面 |
| D3 实现深度 | 关键算法和工程细节（提示词组装、知识库注入、插图、抓取、队列、账本）是否到了能直接开发的程度 | 有没有公式、状态机、SQL、约束 |
| D4 可执行性 | 数据模型能否落地，issue 能否直接派发，实测计划是否省点、顺序是否合理 | Prisma 是否完整；issue 粒度和验收标准 |
| D5 合规与风险 | 抓取边界、版权、广告法、禁做行业、实测是否越界 | 是否有绕过鉴权或逆向的倾向；是否识别出原站流程里的灰色做法 |
| D6 一致性 | 全文前后是否自洽，交叉引用是否有效 | 默认值、公式、引用章节前后是否一致 |

## 3. 总体结论

1. **哪份更准确？A 略好。** A 的错误多是措辞和细节层面；B 引用截图文案更精确，但“编造后写成实测”的情况更多（路由、首页卡片、按钮、模板数量），文档出处也错了好几处。对复刻项目来说，**把推测写成事实的危害，比漏写更大**：开发会照着做出原站根本没有的东西。
2. **哪份更好用？A 更适合当主线，B 适合当细节资料库。** A 结构紧凑，「实测/文档/推测」标注清楚，issue 拆得细，可以直接派发。B 的数据模型、SQL 约束、表单全量字段表、合规防线可以直接拿来补 A 的空白。
3. **两份共同的盲点（终版需要补上）：**
   - 都把「多标签页」当成原站的现状。截图显示原站当前是单页模式，site-map 第 38 行说明多标签只是布局面板里的一个开关。但用户明确要求底座包含多标签页，所以**照做，默认开启，并保留开关**。
   - 都没有对 SOP 复刻指令（`docs/03-sop.md` 第 984–997 行）里「把文章推荐的第一个品牌换成【xxxx品牌】」做合规评估。这属于冒用他人内容并误导读者，终版的系统默认模板不内置这一条。
   - 都没有注意到原站编辑器的工具栏（「代码语言」「段落格式」「HTML」）是 UEditor 风格，选编辑器时可以参考。
   - 配额口径（存量还是累计）、知识库加价是记一条 15 点还是 10+5 两条、批量复刻的真实单价，两份都只是推测，需要按 F06 的计划实测。
4. **终版取舍**：以 A 的结构和底座拆分为主；数据模型以 B 为底本，再精简（去掉零拷贝引用计数、宽度硬拒）；计费采用「整单冻结、逐篇结算」，默认影子计费；多标签页默认开启。具体见 F01 决策记录。

## 3. 遗漏

1. **「返回上一级」按钮**：写作标题（`03`、`04`）、文章分类（`14`）、文章列表（`18`）的工具栏都有这个按钮，A 全部没写。这决定了“从主词下钻到问题”“从分类下钻到文章”的导航交互。
2. **按钮顺序**：关键词页和知识库页是「添加、刷新、删除」，其他页是「刷新、添加、删除」，A 没区分（属于还原细节）。
3. **余额明细**（`27-balance-history.png`）没有复选框和序号列，A:L369 只列了列名，没指出这个差异。
4. **「查看说明」具体在哪些字段**：只有产品服务、产品特点、用户痛点、信任背书、客户案例 5 个字段有；品牌故事、其他信息没有。A:L124 只写了“部分字段”。说明弹窗（`10`）的结构是「内容 / 说明 / 实例」加一个「确定」按钮，A 也没写。

## 5. 过度推测或设计风险

1. **把推测当成依据**：A:L272 用“写作任务里图库是必填项”来印证“K=0 时也要取 1 张封面”，推理不够。图库必填也可能只是为了以后发布用。
2. **Prisma 草图不能直接用**：没有定义 enum（Role、OptStatus、KbStatus…），也没有 `@relation`（例如 `User.wallet Wallet?` 缺少反向关系，`prisma validate` 会报错）。但 #2 的验收写的是“`prisma migrate dev` 成功”（A:L398-L575、L696），不改就过不了。
3. **影子计费下 delta=0** 的处理是对的，但没说清影子模式下余额不足要不要拦截、配额要不要照常校验。
4. **「AI写作数量不回退（按累计算）」**写成了定案，其实是推测（A:L393），应该列入实测。
5. **用 SSE 和每 5 秒轮询二选一**没有给出决策（A:L222）。

## 6. 小结

A 是“准确度够用、结构清楚、能直接派发”的报告。主要问题是：对原站多标签页和首页趋势判断有误；正文和结论的计费方案前后不一致；数据模型只是草图。终版保留 A 的主线结构、issue 粒度和实测策略，修正上述错误，用 B 的 schema 补齐数据模型。

## 5. 过度推测或设计风险

1. **宽度小于 500px 直接拒传**（B:L246、L1673）：SOP 第 1069 行原文是“宽度**建议**不要低于 500px”，而且“系统都会进行图片裁剪”。硬拒会挡掉合法的小图，应改为警告。
2. **零拷贝引用计数**（B:L665）：只是为了让 AI 生图存入图库时不重复占用配额，就引入了 `ref_count`。其实让生图结果本身就作为一条 `MediaAsset`（分类为空），“存入图库”只改分类 ID，就能达到同样效果，复杂度低得多。
3. **22 套系统模板**（B:L331-333、L1659）：数量多、命名自造，种子数据成本高；一期 10 篇文章 + 7 个标题 + 1 个复刻（按 SOP 结构自写）就够了。
4. **搜索 API 摘要直接当正文改写**（B:L588）：等于转载第三方索引的内容，版权风险更高，“成功率 90% 以上”也没有依据。
5. **实测看网络面板**（B:L1826）：虽然只是“只看不改”，但已经在探究原站接口，超出“只看界面”的边界。终版删除这一步。
6. **SHADOW_FREE 下允许透支**（B:L789）：语义不清。影子模式应该是“不实扣、不拦截，只记录原价”，不存在透支的概念。
7. **AI蒸馏「成功 ≥5 条才扣点」**（B:L169）：阈值是自定的，可以保留，但要写成可配置项。
8. **大量表格把推测枚举写成事实**：优化状态「优化中 / 已暂停 / 未开始」、任务状态「部分完成」、操作列按钮清单（B:L152、L217、L355、L449），都没有标「推测」。

## 6. 小结

B 是“信息量最大、工程最深”的报告，数据模型、SQL 约束、表单全量表和合规防线都可以直接复用。但「伪实测」和「出处错误」偏多，前后一致性也最弱，**不能直接当作需求说明书**，每一处都要经过 V01–V04 复核后再采纳。
